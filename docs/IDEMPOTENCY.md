# Ідемпотентність операцій запису

Код: [`app/idempotency.py`](../app/idempotency.py), функція `add_reading` в [`app/main.py`](../app/main.py). Тест: [`tests/test_idempotency.py`](../tests/test_idempotency.py).

## Яку проблему це розв'язує

Клієнт надіслав `POST /devices/7/readings` і не отримав відповіді: обірвалося з'єднання або сплив тайм-аут. Він не знає, чи запис виконано. Якщо повторити запит, у базі може з'явитися два однакові показники. Якщо не повторювати, показник може бути втрачено.

`POST` не є ідемпотентним за визначенням: кожен виклик створює новий запис. Заголовок `Idempotency-Key` робить повтор безпечним: клієнт генерує унікальний ключ для операції й надсилає його з кожною спробою.

## Як це працює

```http
POST /devices/7/readings
Idempotency-Key: 4f2c1c0e-5b0e-4c57-9d0b-0b1a3c9f2a11
Content-Type: application/json

{"temperature": 21.5, "humidity": 40}
```

Ключ у Redis: `idem:reading:{device_id}:{Idempotency-Key}`.

| Ситуація | Що робить сервіс | Відповідь |
|---|---|---|
| Ключ бачимо вперше | займає ключ (`SET NX`), виконує запис, зберігає код і тіло відповіді на **24 години** | `201` або `202` |
| Ключ уже є, результат збережено | операцію **не виконує**, повертає збережену відповідь | та сама відповідь + заголовок `Idempotency-Replayed: true` |
| Ключ є, але перший запит ще виконується | нічого не виконує | `409 Conflict` |
| Перший запит завершився помилкою | звільняє ключ, щоб клієнт міг повторити | помилка |
| Заголовка немає | звичайний запис, як раніше | `201` або `202` |

Деталі:

- `SET NX` — атомарна операція Redis «записати, якщо ключа ще немає». Вона захищає від двох однакових запитів, які одночасно потрапили на різні екземпляри: лише один із них займе ключ.
- Позначка «виконується» живе 60 секунд. Якщо екземпляр упав посеред операції, ключ звільниться сам.
- Redis спільний для всіх екземплярів, тому повторний запит може потрапити на будь-який із них.
- Якщо Redis недоступний, запис виконується без перевірки ідемпотентності: доступність сервісу тут важливіша.

## Тест

```bash
python3 tests/test_idempotency.py "$(terraform -chdir=terraform output -raw alb_url)"
```

Тест створює пристрій, двічі надсилає однаковий запит з одним ключем, порівнює відповіді та рахує записи в базі; потім надсилає запит з іншим ключем.

Результат у синхронному режимі ([`idempotency-sync.txt`](../loadtest/results/idempotency-sync.txt)):

```text
Створено тестовий пристрій id=21, показників: 0
Запит 1: 201 {'id': 17209, 'device_id': 21, 'temperature': 21.5, 'humidity': 40.0, 'created_at': '2026-11-11T20:54:34.467317Z'}
Запит 2: 201 {'id': 17209, 'device_id': 21, 'temperature': 21.5, 'humidity': 40.0, 'created_at': '2026-11-11T20:54:34.467317Z'}  Idempotency-Replayed=true
Показників у базі після двох однакових запитів: 1
Після запиту з ІНШИМ ключем: 2
OK: два однакові запити -> один запис у базі, дві однакові відповіді
```

Два однакові запити дали **один запис у базі** (`id=17209`) і **дві однакові відповіді**.

## Як це поєднується з чергою

У режимі черги ([`QUEUE.md`](QUEUE.md)) дублікати можуть виникнути у двох місцях, і кожне закрите окремо.

**1. Клієнт повторив запит до API.** Працює той самий механізм: повторний запит з тим самим ключем отримує збережену відповідь `202` з тим самим `request_id`, і друге повідомлення в чергу **не потрапляє**.

**2. Черга доставила повідомлення двічі.** SQS гарантує доставку «щонайменше один раз», тож обробник може отримати те саме повідомлення повторно. `request_id` повідомлення служить ключем ідемпотентності вже для обробника: після запису в базу він ставить у Redis позначку `processed:{request_id}` на 24 години, а перед обробкою перевіряє її (`already_processed` в [`app/worker.py`](../app/worker.py)).

Результат тесту в режимі черги ([`idempotency-async.txt`](../loadtest/results/idempotency-async.txt)):

```text

Запит 2: 202 {'request_id': '76da52bf-83d9-4460-9196-f8a65ff92591', 'status': 'queued', 'status_url': '/readings/requests/76da52bf-83d9-4460-9196-f8a65ff92591'}  Idempotency-Replayed=true
```

## Обмеження

- Захист обробника не атомарний. Якщо обробник упаде після `commit` у базу, але до запису позначки `processed`, повторна доставка створить дублікат. Повністю надійний варіант — унікальний стовпець `request_id` у таблиці `readings`: тоді дублікат відхиляє сама база.
- Сервіс не перевіряє, що повторний запит має те саме тіло. Запит з тим самим ключем, але іншими даними отримає стару відповідь.
- Redis у цій роботі не зберігає дані на диск. Після його перезапуску ключі зникають, і повтор виконається як новий запит.
