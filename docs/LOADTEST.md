# Навантажувальне тестування

Сценарій: [`loadtest/script.js`](../loadtest/script.js) (k6). Запуск: [`loadtest/run.sh`](../loadtest/run.sh). Сирі звіти: [`loadtest/results/`](../loadtest/results/).

## Команда запуску

```bash
./loadtest/run.sh
```

Скрипт сам бере адресу сервісу з `terraform output alb_url`. Іншу адресу можна задати змінною `BASE_URL`. Додаткові параметри передаються в k6:

```bash
./loadtest/run.sh -e VUS=80 -e STEADY=5m
```

## Профіль: мало записів, багато читань

Один віртуальний користувач у циклі виконує 1 запис і 9 читань (співвідношення 1 : 9):

| № | Запит | Тип | Відповідник із методички |
|---|---|---|---|
| 1 | `POST /devices/{id}/readings` | запис | створення поста |
| 2, 5, 8 | `GET /devices` | читання | список постів |
| 3, 6, 9 | `GET /devices/{id}` | читання | дані автора |
| 4, 7, 10 | `GET /devices/{id}/readings?limit=50` | читання | пост за ідентифікатором |

У запиті № 4 перевіряється, що щойно створений показник уже є у відповіді (перевірка `new reading is visible`). Пристрій обирається випадково з 20, які функція `setup()` створює перед тестом, якщо їх ще немає. Між запитами пауза 0,3 с.

## Параметри

| Параметр | Типове значення | Зміст |
|---|---|---|
| `VUS` | 60 | N — кількість користувачів на сталому навантаженні |
| `RAMP_UP` | 3m | фаза 1: наростання від 0 до N |
| `STEADY` | 5m | фаза 2: стале навантаження |
| `RAMP_DOWN` | 2m | фаза 3: спад до 0 |
| `THINK` | 0.3 | пауза між запитами, с |
| `BASE_URL` | з Terraform | адреса сервісу |

Тест триває 10 хвилин.

### Як підібрано N

Пробний прогін із 5 користувачами дав ≈ 2,2 запита/с на користувача. Один екземпляр (0,25 vCPU) без кешу витримує близько 80–90 запитів/с при 100 % процесора. При N = 60 попит становить ≈ 170 запитів/с, тобто один екземпляр гарантовано перевантажений, і масштабування спрацьовує ще під час наростання. При N = 50 і наростанні за 2 хв масштабування теж спрацьовувало, але надто пізно (див. перший прогін у [`AUTOSCALING.md`](AUTOSCALING.md)).

Усі прогони — 11.11.2026, сервіс стартує з одного екземпляра.

| Показник | Перший прогін (N = 50, до налаштування) | Без кешу (N = 60) | З кешем (N = 60) |
|---|---|---|---|
| Кількість запитів | 37 411 | 63 031 | 70 991 |
| Запитів за секунду | 69,1 | 104,7 | 117,6 |
| Частка помилок | 0,005 % (2) | 0,002 % (1) | 0,003 % (2) |
| Латентність p50 | 202,4 мс | 46,5 мс | 43,3 мс |
| Латентність p95 | 599,3 мс | 389,6 мс | 276,7 мс |
| Латентність p99 | 699,7 мс | 487,7 мс | 397,7 мс |
| Максимум | 1,10 с | 0,77 с | 1,14 с |
| Перевірки (`checks`) | 99,99 % | 99,99 % | 99,99 % |
| Файл звіту | — | `nocache.txt` | `cache.txt` |

Основним для завдання є прогін «без кешу»: саме під час нього зроблено знімки панелі та отримано листи сповіщень.

### Латентність p95 за операціями

| Операція | Без кешу | З кешем |
|---|---|---|
| `POST /devices/{id}/readings` | 406,9 мс | 340,1 мс |
| `GET /devices` | 382,4 мс | 199,3 мс |
| `GET /devices/{id}` | 324,4 мс | 197,0 мс |
| `GET /devices/{id}/readings` | 394,3 мс | 327,8 мс |

### Як читати ці числа

- Медіана (p50) ≈ 45 мс майже повністю складається з мережевої затримки між тестовою машиною і регіоном eu-north-1. Половина запитів обслуговується без черги.
- p95 і p99 формуються в перші хвилини тесту, коли єдиний екземпляр працює на 100 % процесора, а нові ще запускаються. Після появи трьох екземплярів латентність повертається до рівня медіани.
- Поодинокі помилки (1–2 на десятки тисяч запитів) — це відповіді 5xx у моменти перемикання екземплярів.
